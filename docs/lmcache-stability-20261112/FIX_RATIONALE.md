# LMCache 修复交付：仅保留旧 GPU 验证通过的增量

本次产品改动只包含两项：完整前缀命中的长度边界修复（R2），以及同一请求多次 STORE 的完成事件回收（S）。两项曾随旧 R2＋M＋S 组合通过定向 GPU 用例；本次将其中 R2、S 的原修复增量合入最新私人开发基线。**去掉其他候选后的新组合尚未进行 GPU 回归，不宣称其完整稳定性已经通过。**

## 1. 完整前缀命中时，加载长度与目标 GPU 块数量不一致

当模型启用 prefix replay，且请求恰好完整命中缓存时，原逻辑会为计算下一个 token 保留最后一个输入 token。调度器还会把可加载的前缀向下对齐到 GPU block 边界，再分配加载目标块。但 LMCache 内部仍可能保留完整命中长度，并按完整长度读取缓存。这会导致读取端需要的 block ID 多于调度器实际分配的数量，在真正提交 H2D 之前报 `RETRIEVE block ID underflow`。

修复在插件构造连接器时识别实际 cache group 是否启用 prefix replay，提前启用上游已有的“LOOKUP 保留末 token”开关。查询、读取锁、retrieve 跟踪长度和调度分配因此使用相同前缀。既有 eager lookup 和重新 lookup 也经过该开关，不在 H2D 时临时截断数据。

例如输入 131072 token、chunk 为 1024 时，可复用前缀调整为 130048 token（127 个 chunk），尾部 1024 token 重新计算。输入多出一个 token 时，131072-token 前缀可以按其实际边界复用。没有启用 prefix replay 的模型保持原行为。

涉及 `lmcache_iluvatar/integration/vllm/lmcache_mp_connector.py`。保留最新基线中同事已实现的 STORE replay accounting，不覆盖其修改。

## 2. 同一请求多次 STORE，较早的完成事件可能无人消费

长输入会分批计算并多次保存 KV。原 adapter 按请求 ID 只保留最新一次 STORE 的 future。若旧操作的回复较晚，最新操作先被消费，之后又没有新的 STORE 驱动旧上下文轮询，旧 future 对应的完成事件便可能没有发出 `RELEASE_EVENT`。

旧现场中，一条 132096-token 直接 P 请求已成功返回，但 MP 仍有 11 个未释放导出事件，持续至少 157 秒。它不是“请求还在解码”所必需的正常缓存占用。

修复按请求保留全部尚未消费的 STORE future。每次查询遍历全部成员；已经真实完成的成员消费原结果，未完成的继续保留；所有成员完成后才报告该请求发送完成。新 STORE 成功提交后清除该请求的旧完成标记。不同请求独立推进，不新增全局等待，不以超时或异常伪造设备完成，也不强制释放仍被使用的 GPU 块。

涉及 `lmcache_iluvatar/v1/store_future_group.py`，由 `lmcache_iluvatar/integration/patch/runtime.py` 接入。此修复只处理健康路径中完成事件的消费问题；MP 真正退出、旧 context 退休、session 超时及异常设备传输仍需独立修复和验证。

## 3. 旧 GPU 证据的适用范围

旧 R2＋M＋S 组合完成 16 组、48 次直接 P 长度边界调用，另有 9 次完整 P/D HTTP 调用（包括资格检查及预置缓存请求）；长输入 fixture 的两次冷请求与一次热读完整 D 输出一致。健康 STORE 导出事件回收检查通过。

这些结果支持上述两项增量的定向效果，不等价于全量精度通过，不证明去掉旧 M 后的新组合通过，也不覆盖 P/D/MP 真正退出重入。

本次最新私人开发基线：lmcache-iluvatar `830410db4b34`，其 LMCache 子模块 `ad569120b05f`；vllm-iluvatar `b430966c28c8` 已包含 `byteDance_dsv4.1` 的 `e40282e3836e`。上游 LMCache 和 vLLM 均无本任务源码修改。
