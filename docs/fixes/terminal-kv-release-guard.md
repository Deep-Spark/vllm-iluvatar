# 终止请求的 KV 收发完成与块释放顺序修复

## 原问题

请求被取消时，接收 KV 的异步工作可能尚未完成；连接器同时还可能承诺向调度器报告发送完成。这两项责任需要分别结束。

原 Scheduler 分别处理接收和发送完成。接收完成分支可以先调用 `_free_blocks`，并从 `requests` 删除请求。稍后处理同一请求的发送完成时，`assert req_id in self.requests` 失败，导致 Prefill Engine 退出。两个通知在同一次轮询返回时也存在风险；仅从本次发送集合中扣除接收集合，无法处理跨轮询的情况。

2026-11-15 的单机 2P1D 对照中，同一请求的接收、发送完成相隔 111.159 毫秒。原释放流程在两个通知之间删除请求，释放返回后 109.723 毫秒到达的发送完成触发上述断言。客户端的其他请求仍可成功，因此仅检查 HTTP 成功率不足以发现该节点故障。

## 修改方法

新增 `patch_terminal_kv_release_guard.py`，通过 vllm-iluvatar 原有补丁入口注册。上游 vLLM、LMCache 及定版服务脚本不作业务修改。

- 仅处理已经结束、原流程明确要求等待接收完成、使用带完成来源信息的 MultiConnector 且没有 EC connector 的请求。
- 保留原连接器返回的发送责任，按同一个 Request 对象分别记录最终接收、发送完成。若原连接器未承诺发送责任，则只等待接收完成。
- 两项责任均完成后，调用原 `_free_blocks` 一次。保留原调度 step 的延期释放及全部 worker 完成条件。
- 仍先执行原 MultiConnector 的完成过滤。未知请求、重复最终通知和原释放异常继续报错，不删除原断言，不把异常当作完成。
- 安装时校验被包装的原消费方法及已有补丁顺序，避免在未知调用链上直接套用。

这里的“发送完成”是连接器的逻辑完成通知；它不意味着该请求一定执行过实际 STORE。父层释放方法返回也不等于已测得底层物理显存释放。

## 开关

该保护默认启用，不设置环境变量等同于设置为 `1`。如需回到原行为，在服务 Python 进程及其 Engine 子进程启动前设置：

```sh
export VLLM_ILUVATAR_TERMINAL_KV_OWNERSHIP=0
```

设置为 `0` 时关闭本保护；不设置或设置为 `1` 时启用。该开关在补丁注册时读取，不支持对已运行的 Engine 动态切换。启用后应确认实际 Engine 已安装保护，不能仅凭启动命令或 `/proc/PID/environ` 的初始环境快照判断。测试用的 `VLLM_ILUVATAR_TERMINAL_KV_OBSERVE`、Engine 状态打点和软件暂停点不属于本次产品提交，也不是保护的运行依赖。

## 验证

候选源 SHA256：`c5695cff1e8f5b91bd3942ac5d08ad012d540e16c0dcc9bec65c9c92f9d72b65`。

29 项实际方法 CPU 测试通过，覆盖同次返回、两种跨轮顺序、缺少任一方向、无发送责任、重复通知、未知请求断言、延期释放以及实际补丁入口等。

2026-11-16 将默认值调整为启用后，上述29项回归再次通过；另检查未设置、显式0和显式1三种注册分支，分别为启用、关闭和启用。收发完成及释放方法的AST保持一致。本次默认值调整没有新增GPU测试范围，GPU结论仍以前述显式启用场景为准。

GPU 使用独立单机 2P1D：P 为 PP8，D 为 TP1/DP16，LMCache 开启、chunk 1024、MP 512GiB。修复版运行在 49，对照运行在 15；两边使用相同软件与观测代码，分别明确开启和关闭本保护。实际 Engine 的实例方法和补丁状态均在请求前核实。基础镜像为 `lsun_build_sdk:20261103`，镜像 ID 为 `99c1f8f79570`。源码基线为 vLLM `6919d781a6`、vllm-iluvatar `38d750c423`、LMCache `ad569120b0`、lmcache-iluvatar `e94676e670`、UCX `fa254909ca`、NIXL `25436c1ed6`、ixinfer `bf2f6877f8`、ixformer `dca7f412d5`、vllm-router `8c23b5d3c2`，服务脚本 `faea90419f`。诊断副本另包含已披露的注册控制候选及打点，未合入这些基线提交。

在 128Ki 输入跨 P 读取、H2D 已完成但结果尚未应用的阶段取消目标请求：

- 关闭保护：接收完成后先执行原释放；接收与发送通知相隔 111.159 毫秒，迟到的发送完成触发原断言，P2 Engine 退出。
- 开启保护：接收完成约 121 毫秒后收到发送完成；两者均完成后调用原父层释放一次，请求逻辑退休，未触发该断言。
- 开启保护的运行共提交 6 条 HTTP 腿，组成 5 个逻辑流程。目标双腿按计划取消，其余 4 个流程成功，客户端均退出。第 0 秒仅 seed 所在 P 的 KV 使用率有暂态值；60 秒和 180 秒检查的 68 项指标均为零，无缺失，会话数三个时间点均为零。

两轮业务检查结束后的 D 清场日志仍分别有 8 条和 7 条原生 SIGSEGV 记录，属于已有的独立待定位问题；不能因为脚本退出码为 0 或 GPU 占用归零就忽略。关闭保护及更早的无故障注入运行也出现过该现象，当前未定位其原生调用点。

上述间隔用于说明事件先后，不是性能提升数据。这是一个有限场景的 GPU 验证；完整冷热请求与节点故障组合、底层物理释放及性能影响尚未验证。本保护不解决取消后 MP 会话删除又重新创建、P/D 重入或退出阶段原生崩溃等其他问题。
