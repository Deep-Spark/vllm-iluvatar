# 空闲 Prefill 节点的取消完成通知推进

本改动以已提交的 M2 修复 `030c880516e00448d723aceabadc5ea521931330` 为父版本，只修改 vllm-iluvatar。LMCache、lmcache-iluvatar、Router、原生库和服务参数均不变，不包含独立心跳或诊断补丁。

## 原逻辑与错误链

Decode 可以先为请求分配 KV，再等待 Prefill 写入。若此时客户端取消，Decode 会向 Prefill 发起带请求代际的 ownership_cancel，并保留块，直到取得真实的生产端终态证明。

Prefill 的控制线程能够接收取消、把工作下发到各 worker。但主引擎已经没有模型请求时，可能进入输入队列的阻塞等待；原有“是否还有推送工作”判断没有包含这批取消完成通知。结果是 worker 的实际终态没有继续送入既有聚合和 ownership 回复流程，Decode 持续等待，块也持续保留。

仅把待取消请求加进工作判断仍不充分：主引擎若已经阻塞在输入队列，就需要一次真实唤醒，才能重新检查该状态。

## 新逻辑

1. Producer 按请求标识和代际登记尚待完成证明的取消。收到有效取消时，先登记，再沿原路径下发；重复同代取消合并。
2. 把这些待处理请求纳入 `has_pending_push_work`，并向引擎原输入队列发送已有的 `WAKEUP` 消息。不新增轮询线程、不定时生成模型请求。
3. 每个引擎第一次进入 `_process_input_queue` 时绑定唤醒回调，覆盖插件在构造过程中加载的时序；绑定前已积压的取消也会被唤醒。回调不持有引擎的强引用。
4. 原有 worker 聚合确认全部参与 rank 完成后，继续走原 ownership 事件。控制线程先保留同代终态记录，再清理该代待处理项并回复等待方。唤醒本身、单个 worker 完成、事件刚入队都不能清除这项等待。

本补丁保留原 ACK、代际校验、父调度器释放和 NIXL 原生终态规则。M2 保留的 child 来源与固定 worker 屏障仍然有效。旧代完成不能清掉新代等待；本改动不解决同一请求标识跨代复用的所有生命周期问题。

## 本轮实际验证

环境为 192.168.77.11 的本任务 2P1D 容器，DeepSeek-V4.1-Flash-1017-W4A8，P 的 GPU 内存比例 0.80、D 为 0.945，P 失败策略 recompute、心跳 30 秒。LP 为 `e94676e670`、LMCache 为 `ad569120b0`，vLLM 为 `6919d781a6`。C 的三个产品文件与实际加载的阶段 wheel 字节一致，原生库未变。

* **空闲生产端取消对照：** 两个版本均只发送一条 2048 token 的 Decode 请求，真实观察到同一请求的分配后取消；Prefill 前端请求数为 0，尾窗内没有新增推理请求驱动完成。M2 对照的 D0 KV 使用量在实际 +90.634 秒和 +380.167 秒仍为 `0.003884826325411317`。叠加 C 后，实际 +10.826、+63.047、+182.566 秒均为 0，P 和 MP 相关软件资源也为 0，原服务身份和健康保持稳定。
* **正常数据路径：** 8 条 HTTP 请求覆盖两个普通 P 写缓存请求、冷 PD、热 JSON PD 和热流式 PD。两次热读均观察到同一请求的 7/7 对象预取、7 条各 1024 token 的 MP 读取日志、P 外部命中增加 1024、D 外部传输增加 2048，两端本地前缀命中增量均为 0。JSON 的完整文本和 32 个 token ID、流式完整文本均与当前冷请求一致；最后 0/60/180 秒尾窗资源为 0。
* **长请求双腿取消回归：** 131072 token 的 P2/D0 两条请求均在真实分配后，仅取消 D 客户端。D 客户端在约 89.8 毫秒结账，未取消的 P2 在 5.617 秒独立成功并读到 EOF；这两个时间不代表物理传输完成时间。0/60/180 秒的实际检查分别约为 +10.737、+62.475、+182.233 秒，所选资源均为 0，服务身份稳定，八类严重错误均为 0。

CPU 证据另包含待取消先于回调绑定、空闲输入队列被实际 WAKEUP 唤醒、重复取消合并、唤醒失败保留等待、旧代完成不清新代、非 Producer 旁路与弱引用生命周期等合同。实际安装环境验证了公共插件加载与既有 M2 聚合类共存。

## 结论边界

以上支持“空闲 Producer 取消完成通知不能停在未消费状态”这一目标及所列回归。D0 的终态日志与源码的 ACK 代际检查共同支持取消握手完成；这不是网络 ACK 抓包。空闲目标有 8 条 worker 完成日志，其中 1 条因输出交织缺少进程前缀，不能仅凭这些日志独立证明八个不同 rank。

软件资源归零不等于全局物理 DMA/fence 证明。当前 C 新代只实际使用 D0，D1–D15 未出生的普通队列指标保留为未覆盖；没有完成全 D 压力、完整故障矩阵、GPQA 或性能验收。本改动不解决心跳失健、MP 死亡后的物理资源回收、原 MIX64 的超时与 session 残留，也不把未发生的阶段说成已经验证。
